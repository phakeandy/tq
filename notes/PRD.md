# 分布式任务引擎 — 产品需求文档

## 产品概述

一个异步任务处理系统。生产者提交任务，系统保证任务被可靠地消费执行，并在任务失败时自动重试。

---

## 用户故事

### 生产者视角

- 作为业务系统，我希望能提交一个异步任务，指定任务类型和参数，并得到一个任务 ID 用于后续查询。
- 作为业务系统，我希望任务可以延迟执行——比如"30 分钟后执行"。
- 作为业务系统，我希望能防止同一个任务被重复提交（幂等）。
- 作为业务系统，我希望提交的任务最终被执行，即使执行过程中发生了临时性失败。

### 运维者视角

- 作为运维者，我希望系统在关闭时不会丢失正在执行的任务——等待它们完成后再退出。
- 作为运维者，我希望即使 Worker 意外崩溃（宕机、被杀），正在执行的任务也能被自动恢复，而不是永远卡在执行中。
- 作为运维者，我希望已完成任务的结果能保留一段时间供查询，过期后自动清理，不无限占用存储。
- 作为运维者，我希望可以按状态、按时间枚举任务，用于排查问题和统计。

## 功能需求

### F1：任务提交

系统接受外部提交任务。每个任务包含：

| 字段 | 说明 | 必填 |
|------|------|------|
| 任务类型 | 标识任务由哪类 Worker 处理 | 是 |
| 参数 | 任务的业务数据，对引擎透明 | 是 |
| 最大重试次数 | 失败后最多重试几次 | 否（默认 3） |
| 幂等键 | 相同幂等键的任务只执行一次 | 否 |
| 延迟时间 | 延迟多久后执行 | 否（默认立即） |
| 超时时间 | 单次执行的最长允许时间 | 否（默认 30s） |

提交成功后返回任务 ID，后续可通过该 ID 查询状态和结果。

### F2：即时执行

对于未指定延迟时间的任务，在 Worker 可用时立即执行。

### F3：延迟执行

对于指定了延迟时间的任务，在延迟时间到达后再交给 Worker 执行。

### F4：任务重试

- 任务执行失败后自动重试。
- 重试间隔随失败次数递增（第一次失败等 1 秒，第二次等 2 秒，第三次等 4 秒……）。
- 达到最大重试次数后停止重试，标记为最终失败。

### F5：幂等投递

对于指定了幂等键的任务：
- 如果已有相同幂等键的任务尚未完成，拒绝提交。
- 如果已有相同幂等键的任务已完成，直接返回原有结果。

### F6：任务状态查询

通过任务 ID 查询任务当前状态。状态包括：

- 等待中：已提交，等待 Worker 拉取
- 执行中：已被 Worker 拉取，正在执行
- 成功：执行完成
- 重试中：执行失败，等待重试
- 最终失败：已达到最大重试次数

查询返回当前状态及（如果已完成）执行结果。

### F7：多 Worker 并发执行

系统同时运行多个 Worker 并行处理任务。Worker 数量可配置。

### F8：超时终止

若任务执行时间超过设定的超时时间，中止该次执行并视为失败，触发重试。

### F9：Worker 故障隔离

单个任务执行过程中的异常不影响 Worker 继续处理下一个任务。Worker 不会因某个任务崩溃而退出。

### F10：优雅关闭

系统收到关闭信号后：
- 不再接受新任务
- 等待正在执行的任务完成
- 然后再退出

不会因为关闭而导致正在执行的任务丢失或中断。

### F11：可观测

系统对外暴露以下指标：
- 任务提交总数
- 按结果（成功/失败/超时）分类的任务完成数
- 当前队列中等待执行的任务数
- 任务从提交到完成的耗时分布

### F12：崩溃恢复（租约机制）

Worker 在执行任务过程中异常退出（进程被杀、宕机、网络分区）时，任务不能被永久卡在"执行中"状态：

- 任务从待执行队列取出进入执行中状态时，同时写入一个租约（lease），记录到期时间。
- Worker 执行期间周期性地续租（心跳）；租约未到期前，其他 Worker 不得领取该任务——保证同一时刻只有一个 Worker 执行（与 N2 呼应）。
- 系统周期性扫描租约到期的任务：
  - 若该任务还有剩余重试次数，按 F4 的重试规则重新调度执行；
  - 若已无重试次数，标记为最终失败。
- 任务被回收的时延 = 租约时长（可配置，默认 30s），即"崩溃 → 恢复"的最大间隔。
- 崩溃恢复采用"至少一次"语义：Worker 可能在完成执行但尚未标记完成时崩溃，任务会被重新执行一次，业务方需容忍重复执行（幂等）。
- 与 F10 的区别：F10 处理正常关闭（等任务跑完再退出），F12 处理异常死亡（任务被租约机制接管）。

### F13：结果保留与按时间清理

- 已完成的（成功/最终失败）任务结果按配置的保留期保存，保留期内可通过 F6 查询。
- 超过保留期的任务结果由后台清理器自动删除。
- 清理以完成时间为索引，按时间范围批量删除，不逐条扫描全库。
- 保留期可配置，默认 1 小时；支持按状态区分保留期（如失败任务保留更久供排查）。

### F14：任务枚举

- 运维可列出各状态（等待中/执行中/成功/最终失败）下的任务明细，支持按时间范围过滤。
- 用途：故障排查（"昨天失败的任务有哪些"）、抽样统计、批量操作（如重新入队、清理）。
- 与 F11 的区别：F11 提供聚合指标（计数、速率），F14 提供具体任务条目（明细）。

## 非功能需求

### N1：可靠性
- 已提交但尚未执行的任务在系统重启后不丢失。
- 执行中的任务在 Worker 异常退出后不丢失：租约到期后自动重新调度（F12）。
- 幂等键去重必须在并发提交同一幂等键时仍然有效。

### N2：正确性
- 同一个任务不会被两个 Worker 同时执行（含租约未到期时的崩溃恢复场景，F12）。
- 延迟任务在原定时间之前不会被消费。

### N3：性能

- 在 100 Worker 并发下，系统能稳定处理每秒 500 次任务提交。
- 延迟任务的调度精度在秒级以内。

### N4：原子性
- 保证业务上的原子操作是真的原子操作

---

## 范围边界

### 本期做

- F1–F14 全部功能需求
- N1–N3 非功能需求

### 本期不做

- 定时任务（Cron）：不实现"每天 8 点执行"。延迟任务可替代部分场景。
- 任务优先级：不实现高优先级插队。
- 多节点分布式：单实例部署。多 Worker 但共享同一存储。
- Web 管理界面：通过 API 和指标观测。
- 任务依赖：不支持"任务 B 在任务 A 完成后执行"。
- N4
